# بخش اول: آشنایی با RPC و فناوری‌های مختلف آن

## 1. تعریف RPC

فراخوانی رویه از راه دور (Remote Procedure Call یا RPC) یک الگوی ارتباطی در سیستم‌های توزیع‌شده است که به یک برنامه اجازه می‌دهد تابع یا رویه‌ای را روی یک ماشین دیگر فراخوانی کند، به گونه‌ای که از دید برنامه‌نویس مشابه فراخوانی یک تابع محلی به نظر برسد. هدف اصلی RPC پنهان کردن جزئیات ارتباطات شبکه‌ای و ساده‌سازی توسعه نرم‌افزارهای توزیع‌شده است.

در RPC، برنامه‌نویس تنها تابع موردنظر را فراخوانی می‌کند و چارچوب RPC مسئولیت برقراری ارتباط شبکه‌ای، ارسال پارامترها، دریافت پاسخ و مدیریت بسیاری از جزئیات ارتباطی را برعهده می‌گیرد. این ویژگی باعث می‌شود توسعه‌دهنده بتواند روی منطق کسب‌وکار تمرکز کند و کمتر درگیر پیچیدگی‌های سطح پایین شبکه شود.

---

## 2. ایده اصلی فراخوانی تابع از راه دور

ایده اصلی RPC این است که یک تابع واقع در سرور از دید برنامه سمت کلاینت مشابه یک تابع محلی نمایش داده شود.

به عنوان مثال، فرض کنید تابعی با نام `Login()` روی سرور احراز هویت وجود دارد. برنامه سمت کلاینت می‌تواند این تابع را همانند یک تابع معمولی فراخوانی کند:

```go
result := Login(username, password)
```

در ظاهر، این فراخوانی تفاوتی با اجرای یک تابع محلی ندارد، اما در پشت صحنه مراحل زیر انجام می‌شود:

1. پارامترهای تابع بسته‌بندی می‌شوند.
2. درخواست از طریق شبکه ارسال می‌شود.
3. سرور درخواست را دریافت می‌کند.
4. تابع واقعی اجرا می‌شود.
5. نتیجه تولید می‌شود.
6. پاسخ از طریق شبکه بازگردانده می‌شود.
7. نتیجه به برنامه فراخوان تحویل داده می‌شود.

---

## 3. تفاوت فراخوانی محلی و فراخوانی راه دور

در فراخوانی محلی، تمام توابع و داده‌ها در یک فضای حافظه مشترک قرار دارند و نیازی به انتقال داده از طریق شبکه نیست. در نتیجه سرعت اجرا بسیار بالا و احتمال خطا پایین است.

در مقابل، در فراخوانی راه دور، ارتباط از طریق شبکه انجام می‌شود. پارامترها باید به قالب قابل انتقال تبدیل شده و از طریق شبکه ارسال شوند. همین موضوع باعث افزایش تأخیر، احتمال از دست رفتن ارتباط و بروز خطاهای مختلف می‌شود.

| ویژگی          | فراخوانی محلی | فراخوانی راه دور |
| -------------- | ------------- | ---------------- |
| محل اجرا       | همان فرآیند   | ماشین دیگر       |
| تأخیر          | بسیار کم      | وابسته به شبکه   |
| نیاز به شبکه   | ندارد         | دارد             |
| احتمال قطعی    | بسیار کم      | بالا             |
| پیچیدگی ارتباط | کم            | زیاد             |
| احتمال Timeout | ندارد         | دارد             |

## 4. نقش Client Stub و Server Stub

برای آنکه RPC بتواند شبیه یک فراخوانی محلی عمل کند، از دو مؤلفه مهم به نام Stub استفاده می‌شود.

### Client Stub

کلاینت استاب در سمت درخواست‌کننده قرار دارد و وظایف زیر را انجام می‌دهد:

* دریافت پارامترهای تابع
* تبدیل داده‌ها به قالب قابل انتقال
* ارسال درخواست به سرور
* دریافت پاسخ
* تحویل نتیجه به برنامه

### Server Stub

سرور استاب در سمت سرویس‌دهنده قرار دارد و وظایف زیر را برعهده دارد:

* دریافت درخواست شبکه‌ای
* استخراج پارامترها
* فراخوانی تابع واقعی
* دریافت خروجی
* ارسال پاسخ به کلاینت

وجود این دو لایه باعث می‌شود برنامه‌نویس درگیر جزئیات سوکت‌ها، بسته‌های شبکه و پروتکل‌های ارتباطی نشود.

## 5. مفهوم Serialization و Deserialization

در ارتباطات شبکه‌ای، داده‌های موجود در حافظه مستقیماً قابل ارسال نیستند. بنابراین لازم است ابتدا به قالبی استاندارد تبدیل شوند.

### Serialization

فرایند تبدیل ساختارهای داده، اشیا یا متغیرها به قالبی قابل انتقال در شبکه را Serialization می‌گویند.

مثال:

```json
{
"username": "alice",
"password": "alice123"
}
```

### Deserialization

فرایند بازسازی داده‌های دریافتی از شبکه و تبدیل آن‌ها به ساختارهای اصلی برنامه را Deserialization می‌گویند.

این دو فرایند پایه اصلی تبادل داده در تمام فناوری‌های RPC هستند.

## 6. مفهوم IDL (Interface Definition Language)
<div dir="rtl">
زبان تعریف رابط یا Interface Definition Language که به اختصار IDL نامیده می‌شود، روشی استاندارد برای تعریف سرویس‌ها، توابع و ساختار پیام‌ها است.

IDL مستقل از زبان برنامه‌نویسی بوده و امکان تولید خودکار کد در زبان‌های مختلف را فراهم می‌کند.

نمونه‌ای از تعریف سرویس در gRPC:

```proto
service AuthService {
rpc Login(LoginRequest) returns (LoginResponse);
}
```

مزایای IDL:

* استانداردسازی رابط‌ها
* کاهش خطاهای توسعه
* تولید خودکار کد
* پشتیبانی از چند زبان برنامه‌نویسی

---

## 7. خطاهای رایج در RPC

برخلاف فراخوانی محلی، RPC با انواع مختلفی از خطاهای شبکه‌ای مواجه است:

### 1. Network Failure

قطع کامل ارتباط شبکه بین کلاینت و سرور.

### 2. Timeout

سرور در زمان تعیین‌شده پاسخ نمی‌دهد.

### 3. Server Crash

سرور در حین پردازش درخواست متوقف می‌شود.

### 4. Serialization Error

تبدیل داده‌ها به قالب انتقال با خطا مواجه می‌شود.

### 5. Version Mismatch

نسخه کلاینت و سرور با یکدیگر سازگار نیستند.

### 6. Packet Loss

بسته‌های شبکه در مسیر از بین می‌روند.

## 8. مقایسه RPC و REST
<div dir="rtl">
REST یک سبک معماری برای طراحی سرویس‌های وب است که بر پایه منابع (Resources) و متدهای استاندارد HTTP طراحی شده است.

در مقابل، RPC بر پایه فراخوانی عملیات و توابع عمل می‌کند.

| ویژگی                   | RPC             | REST           |
| ----------------------- | --------------- | -------------- |
| مدل طراحی               | مبتنی بر عملیات | مبتنی بر منابع |
| سرعت                    | بالا            | متوسط          |
| حجم پیام                | کم              | بیشتر          |
| خوانایی                 | کمتر            | بیشتر          |
| مناسب برای مرورگر       | متوسط           | بسیار مناسب    |
| مناسب برای Microservice | بسیار مناسب     | مناسب          |
<div dir="rtl">
REST معمولاً برای APIهای عمومی و ارتباط با مرورگرها انتخاب می‌شود، در حالی که RPC بیشتر برای ارتباط سرویس‌های داخلی در سیستم‌های توزیع‌شده کاربرد دارد.

## 9. مقایسه فناوری‌های رایج RPC

در این بخش سه فناوری رایج RPC بررسی و مقایسه می‌شوند.

### gRPC
<div dir="rtl">
gRPC توسط گوگل توسعه یافته و از Protocol Buffers برای انتقال داده استفاده می‌کند.

مزایا:

* کارایی بسیار بالا
* پشتیبانی از Streaming
* پشتیبانی از IDL
* تولید خودکار کد
* مناسب برای Microservices

معایب:

* خوانایی کمتر پیام‌ها
* پیچیدگی بیشتر نسبت به JSON-RPC

---

### JSON-RPC
<div dir="rtl">
JSON-RPC یک پروتکل سبک مبتنی بر JSON است.

مزایا:

* ساده و خوانا
* یادگیری آسان
* مناسب برای پروژه‌های کوچک

معایب:

* سربار بیشتر نسبت به gRPC
* عدم پشتیبانی استاندارد از Streaming

---

### XML-RPC
<div dir="rtl">
XML-RPC یکی از قدیمی‌ترین فناوری‌های RPC است که از XML برای تبادل داده استفاده می‌کند.

مزایا:

* سازگاری با سیستم‌های قدیمی
* استاندارد شناخته‌شده

معایب:

* حجم زیاد پیام‌ها
* کارایی پایین
* پیچیدگی بیشتر در پردازش

---

## 11. پاسخ پرسش‌های تحلیلی

### 11-1. چرا RPC باعث می‌شود فراخوانی یک سرویس راه دور شبیه فراخوانی یک تابع محلی به نظر برسد؟

زیرا لایه‌های Client Stub و Server Stub تمام جزئیات ارتباط شبکه، ارسال پیام، دریافت پاسخ و تبدیل داده‌ها را مخفی می‌کنند. در نتیجه برنامه‌نویس تنها یک تابع را فراخوانی می‌کند و احساس می‌کند که تابع به صورت محلی اجرا شده است.

### 11-2. چرا این شباهت می‌تواند خطرناک یا گمراه‌کننده باشد؟

زیرا برنامه‌نویس ممکن است فراموش کند که هر فراخوانی RPC در واقع یک عملیات شبکه‌ای است. این موضوع می‌تواند باعث افزایش تعداد درخواست‌ها، ایجاد تأخیر زیاد، مصرف پهنای باند و کاهش کارایی سیستم شود.

### 11-3. چه خطاهایی در فراخوانی راه دور ممکن است رخ دهد که در فراخوانی محلی وجود ندارد؟

* قطع ارتباط شبکه
* Timeout
* از بین رفتن بسته‌های داده
* خرابی سرور
* ناسازگاری نسخه‌ها
* خطاهای Serialization و Deserialization

### 11-4. در چه شرایطی gRPC انتخاب بهتری از REST است؟

زمانی که:

* معماری مبتنی بر Microservice وجود داشته باشد.
* کارایی بالا اهمیت داشته باشد.
* تعداد زیادی سرویس با یکدیگر ارتباط داشته باشند.
* نیاز به Streaming وجود داشته باشد.
* مصرف پهنای باند باید حداقل باشد.

### 11-5. در چه شرایطی REST انتخاب مناسب‌تری است؟

زمانی که:

* API عمومی برای کاربران خارجی ارائه می‌شود.
* ارتباط با مرورگرها اهمیت دارد.
* خوانایی پیام‌ها مهم است.
* سادگی توسعه و نگهداری اولویت دارد.
* نیاز به سازگاری گسترده با ابزارهای وب وجود دارد.

### نتیجه‌گیری
<div dir="rtl">
RPC یکی از مهم‌ترین فناوری‌های ارتباطی در سیستم‌های توزیع‌شده است که امکان فراخوانی توابع روی ماشین‌های راه دور را فراهم می‌کند. استفاده از مفاهیمی مانند Stub، Serialization و IDL باعث می‌شود توسعه‌دهندگان بتوانند سرویس‌های توزیع‌شده را با پیچیدگی کمتر پیاده‌سازی کنند. در میان فناوری‌های موجود، gRPC به دلیل کارایی بالا و پشتیبانی از Streaming گزینه‌ای بسیار مناسب برای معماری‌های Microservice محسوب می‌شود، در حالی که JSON-RPC و XML-RPC بیشتر برای کاربردهای ساده‌تر یا سیستم‌های قدیمی مورد استفاده قرار می‌گیرند. همچنین انتخاب بین RPC و REST باید بر اساس نیازهای عملکردی، نوع کاربران و معماری سیستم انجام شود.
